# Handoff: the connect path, proved and fixed — 14 August 2026

The 0.2.0 credential rework was wrong about the one thing it could not test,
and running it against a real database found that out in the first hour.
Version 0.4.0 fixes it. Everything below was measured on ins-15 against the
local Oracle 19c instance (`ORCLPDB1`), sqlplus 19c reached through the
`/usr/local/bin/sqlplus` os.execv wrapper.

## The bug

0.2.0 sent `CONNECT user@tns` and then wrote the password on the following
line, reasoning that sqlplus prompts there and reads the answer verbatim.
It does prompt at a terminal. On a pipe it does not prompt at all, and the
line after `CONNECT` is parsed as more `CONNECT` arguments.

Probe method: against an account that exists, a password sqlplus read whole
comes back `ORA-01017`. Anything else means it parsed the line.

    'plainpw'  verbatim  ORA-01017: invalid username/password; logon denied
    'ab@cd'    PARSED    <TIMEOUT>
    'ab/cd'    PARSED    SP2-0306: Invalid option.
    'ab#cd'    verbatim  ORA-01017
    'abcd#'    verbatim  ORA-01017
    'ab!cd'    verbatim  ORA-01017
    'ab"cd'    verbatim  ORA-01017
    "ab'cd"    verbatim  ORA-01017
    'ab cd'    PARSED    SP2-0306: Invalid option.
    'ab$cd'    verbatim  ORA-01017
    'ab%cd'    verbatim  ORA-01017

The `@` case is the nasty one: sqlplus goes off to resolve whatever follows
the `@` as a net service name, and the connect hangs to `connect_timeout`
(or returns `ORA-12543` if the name happens to resolve to an unreachable
host). No error, no clue, just a session that takes 30 seconds to fail.

Watch out for a lockout while probing this. `FAILED_LOGIN_ATTEMPTS` on the
`DEFAULT` profile is 10, and eleven wrong passwords in a row turn every
subsequent result into `ORA-28000` — which reads exactly like a parse
result if you are not expecting it. Set the limit to `UNLIMITED` for the
duration and put it back after.

## The fix

`CONNECT user/"password"@tns`, written to stdin.

The `/nolog` start is what keeps the credential out of the process table,
and that holds wherever on the pipe the password goes. The prompt line was
never buying the security; it was only ever a claim about parsing, and the
claim was false.

Eight accounts, each with a different password, all connect and return
their own username through `SqlplusSession`:

| account | password |
|---|---|
| sps_plain | `Sp1keTest99` |
| sps_at | `aa@bb` |
| sps_slash | `aa/bb` |
| sps_space | `aa bb` |
| sps_hash | `aabb#` |
| sps_quote | `aa'bb` |
| sps_dollar | `aa$bb` |
| sps_awkward | `Sp!ke@1/x#` |

Oracle refuses to create a password containing a double quote — `ORA-03001:
unimplemented feature` — so the doubling in `_quote_password` holds the rule
rather than any password that can exist. There is a unit test for it anyway.

## The other two unknowns, settled

A rejected `CONNECT` does not re-prompt when stdin is a pipe. It writes
`ERROR:` and `ORA-01017` and goes on reading, so the sentinel survives and
the error-scan path fires. Measured at 1.2 s for a wrong password, a
nonexistent user, and an empty password alike. The feared hang-to-timeout
does not happen.

Silent sqlplus never writes `Enter password:` on a pipe. The successful
connect exchange produces exactly one line of output, the sentinel. The
`endswith(sentinel)` matching in `_raw_query` therefore never fires in
practice — it is kept because it is correct, and `FAKE_SQLPLUS_PROMPT`
still exercises it.

A password containing a newline is still untested and still a documented
limitation. It cannot survive: sqlplus reads to end of line.

## Timings, after the change

Twenty queries each, `ORCLPDB1`:

| mode | persistent | per-call | ratio |
|---|---|---|---|
| OS authentication (`/@orclpdb1`) | 14.8 ms | 1346.8 ms | 91.2x |
| password (`sps_plain`) | 15.0 ms | 1289.6 ms | 86.1x |

Connect itself is 0.24 s. The numbers match the pre-rework runs, so nothing
about quoting the password costs anything.

## What changed in the tree

`session.py` — new `_quote_password`; `_connect` builds the login string
instead of writing a password line. Docstrings that asserted the verbatim
rationale are corrected rather than deleted, because the wrong version is
the tempting one and someone will propose it again.

`tests/fake_sqlplus.py` — no longer consumes a line after `CONNECT`.
`FAKE_SQLPLUS_PROMPT` still emits the prompt fragment.

`tests/test_session.py` — 65 tests, about 5.6 s, no Oracle needed.
`test_special_characters_need_no_quoting` is gone; in its place
`test_password_is_quoted_on_the_connect_line` and
`test_embedded_double_quote_is_doubled`.

`tests/test_spike_oracle.py` — quotes the baseline login string, and skips
the baseline outright when the password is not alphanumeric. A Windows
`sqlplus.exe` reached through Cygwin mangles argv quoting whatever you do
with it, which is a fact about the old pattern rather than a test failure.

`setup.py` — reads `__version__` out of `__init__.py`. One place now.

`CHANGELOG.md` — new.
